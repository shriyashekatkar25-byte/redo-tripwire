The decision board

Rename a table, re-pay for every page?

Customer problem

A data engineer keeps an AI document-parsing job in a bundle. They rename the output table in YAML during a tidy-up and run deploy. Because the task is incremental, a new output table means every file in the volume is processed again. The diff looks like one line. The bill can look like a month.

📌 pinned to: who feels the pain

Proposed change

At deploy time, when a change will trigger a full reprocess, sample a few dozen files, estimate the reprocess cost, and stop to ask for confirmation only when the estimate is above a threshold T. In CI, the same gate needs an explicit approve flag.

The question this prototype answers: what should the default T be?

📌 pinned to: the change

Success metric

Missed bill shocks: share of reprocessing redeploys that cost more than the customer's "shock line" and went through with no prompt. Target: ≤ 1%.

📌 pinned to: north star

Guardrails

  • Prompt rate ≤ 15% of reprocessing redeploys (friction)
  • Needless prompts ≤ 35% of prompts (true cost under half the shock line)
  • Estimate error at P90 ≤ ±40%
  • Added deploy time ≤ 3 s (preview sample capped at 60 files)
📌 pinned to: what we won't break

Stakeholders

  • Bundles / CLI eng: owns the deploy gate
  • AI Functions team: cost-per-page model
  • Jobs: incremental state + run semantics
  • FinOps admins: budgets and alerts
  • Support: the "why did my bill jump" tickets
📌 pinned to: who signs off

Options on the table

A. Warn in text only. B. Confirm above T (this model). C. Always block a full reprocess. A is cheap but easy to scroll past; C trains people to add the approve flag by reflex.

Live simulation · seeded · rejection sampling

The redeploy simulation room

Each run plays out 1,200 imaginary redeploys that trigger a full reprocess. For each one, pages per file come from an odd, two-humped shape (short invoices, long contracts) that no built-in sampler covers, so we draw it with rejection sampling. The preview gate sees 60 files; the "true" bill is estimated from a larger, independent 300-file sample scaled to the whole volume.

Memo: default for the reprocess gate

The math, from my Monte Carlo course

Rejection sampling, in plain words

The idea

I want draws from a shape f(x) (pages per file) that I can write down but can't invert. I pick an easy shape g(x) I can sample, and stretch it by a constant M so M·g(x) sits on or above f(x) everywhere, like a tent over a hill.

Then: draw x from g, draw U uniform on [0,1], and keep x only if

U ≤ f(x) / (M · g(x))

The kept points are exact draws from f. The fraction kept is 1/M (when f and g are both proper densities), so a snug tent wastes fewer darts.

Why it matters for this product call

Page counts are lumpy: lots of 1–3 page invoices, a second hump of 30–50 page contracts. A normal or plain exponential would hide the contract hump, and the contract hump is what drives bill shock.

Toggle the envelope above: the flat box keeps only about 6% of darts; a 50/50 exponential-plus-flat tent that hugs the short-doc spike keeps about half. Same answer, cheaper compute. That is also how I'd want the real preview estimator to behave: exact shape, low overhead in the deploy path.

acceptance ≈ 1/M · cost per kept draw ≈ M proposals
How I'd run it on real data

SQL + Python sketch

Illustrative table names. Step 1: find redeploys that changed an AI Function task's input or output table and join to what the next run actually cost.

-- reprocessing redeploys and their real follow-up cost (illustrative tables)
WITH redeploys AS (
  SELECT workspace_id, job_id, task_key, deployed_at
  FROM   ops.bundle_deploy_events
  WHERE  task_type = 'ai_function'
    AND  (output_table_changed OR input_table_changed)
    AND  deployed_at >= current_date() - INTERVAL 90 DAYS
),
next_run AS (
  SELECT r.*, u.pages_processed, u.list_cost_usd,
         ROW_NUMBER() OVER (PARTITION BY r.job_id, r.task_key, r.deployed_at
                            ORDER BY u.run_started_at) AS rn
  FROM   redeploys r
  JOIN   ops.ai_function_task_usage u
    ON   u.job_id = r.job_id AND u.task_key = r.task_key
   AND   u.run_started_at > r.deployed_at
)
SELECT approx_percentile(list_cost_usd, array(0.5, 0.9, 0.99)) AS cost_pcts,
       avg(CASE WHEN list_cost_usd > 750 THEN 1 ELSE 0 END)     AS share_over_shock
FROM   next_run WHERE rn = 1;

Step 2: fit the pages-per-file shape from a sample and back-test thresholds with rejection sampling.

import numpy as np
pages = spark.table("ops.file_page_counts_sample").toPandas()["pages"].to_numpy()

# smooth target f(x) from the sample (kernel density), bounded to [1, 120]
from scipy.stats import gaussian_kde
f = gaussian_kde(pages, bw_method=0.15)
xs = np.linspace(1, 120, 2000)
g = lambda x: np.full_like(x, 1/119)            # flat proposal
M = 1.05 * (f(xs) / g(xs)).max()                # tent height

rng = np.random.default_rng(102)
def draw(n):
    out = []
    while len(out) < n:
        x = rng.uniform(1, 120, 4*n)
        u = rng.uniform(size=x.size)
        out.extend(x[u <= f(x) / (M * g(x))])
    return np.array(out[:n])

for T in [100, 200, 400, 800]:
    est = draw(60).mean()                        # what the deploy gate sees
    print(T, est, "acceptance≈", 1/M)
